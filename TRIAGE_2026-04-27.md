## 🔬 Root cause #1 — your CV is not on the server

**What I observed (live, just now):**
```
GET https://mba-agent-71hu.onrender.com/api/cv/status?telegram_id=1284690336
{
  "data": {
    "has_cv": false,        ← THE BUG
    "keyword_count": 0,
    "top_keywords": [],
    "has_profile": false
  }
}
```

The "For You" engine is healthy — it just has nothing to match
against. With no CV on disk, every listing receives a placeholder
score of `50.0`. The list then sorts by that constant, which
means the order is effectively random — that's exactly the
"Tally Accountant — Agra" / "Public Relations — Bangalore"
garbage you're seeing.

**Why the CV is missing even though you uploaded it:**

Render's **free tier filesystem is ephemeral.** The original
upload code in `core/miniapp_api.py` writes the CV to:

```
data/user_cvs/{telegram_id}.pdf
```

Render wipes the entire `data/` directory on every redeploy and
on every cold restart (which on the free tier happens whenever
the dyno has been idle for 15 minutes). Combined with
`FORCE_DB_RESET=true` in your env (visible in your screenshot
and confirmed in the boot log: `*** FORCE_DB_RESET=true detected ***`),
the user-uploaded CV vanishes silently after every deploy or
restart, and the front-end sends the user back to a neutral
state with no warning.

## 🔬 Root cause #2 — `FORCE_DB_RESET=true` is left enabled

From the production log:
```
2026-04-27 17:25:46 | WARNING | __main__:_init_data_seed:446
[Phase 3] *** FORCE_DB_RESET=true detected ***
[Phase 3] SQLite wiped: {ghost_scores: 0, application_packages: 0,
                          auto_apply_queue: 0, outcomes: 0,
                          clean_listings: 0, raw_listings: 0}
```

This wipes the **local** SQLite cache on every boot. Supabase
data is safe (the safety gate works), but you lose:
- the freshly-scraped listings from the previous scheduler run
- the CV-match scores that have already been computed
- the auto-apply queue

After that wipe, the system has to scrape from scratch again,
which is why your `clean_listings` was 0 right after boot.

**Action required from you:** Remove `FORCE_DB_RESET` from
Render's Environment tab. **Do this before anything else** —
otherwise every deploy of this patch will also re-wipe.

## What is FIXED in this commit

### 1. Encrypted credential vault (`core/credential_vault.py`)

```
┌─────────────────────────────────────────────────────────┐
│  CredentialVault                                        │
│  ┌─────────────────────────────────────────────────┐    │
│  │  master_key (Fernet AES-128-CBC + HMAC-SHA-256)│    │
│  │  ← CREDENTIAL_VAULT_KEY env (preferred)         │    │
│  │  ← SESSION_VAULT_KEY env  (fallback)            │    │
│  │  ← data/.vault.key        (dev only)            │    │
│  └─────────────────────────────────────────────────┘    │
│      ↓ encrypt JSON → ciphertext                        │
│  Supabase: user_portal_credentials                      │
│  ┌─────────────────────────────────────────────────┐    │
│  │  PRIMARY KEY (telegram_id, portal)              │    │
│  │  enc_payload TEXT  (Fernet ciphertext)          │    │
│  │  risk_level  TEXT  (low/medium/high)            │    │
│  │  cred_version INT                               │    │
│  │  saved_at, updated_at TIMESTAMPTZ               │    │
│  └─────────────────────────────────────────────────┘    │
│      Row-level security ENABLED;                        │
│      anon key has zero access; service-role bypasses    │
└─────────────────────────────────────────────────────────┘
```

- **Per-user scoping**: row key is `(telegram_id, portal)`, so user A
  cannot read user B's row.
- **Plaintext only ever in process memory** during an active auto-apply.
  Never logged, never returned through any API.
- **Mirrored to Supabase** — survives Render redeploys.
- **Rotation supported** — `vault.rotate_key(new_key)` re-encrypts every
  row and atomically swaps the key (used when you suspect a leak).
- **GDPR right-to-erase** — `vault.delete_all_for_user(id)` wipes every
  portal blob a user owns.
